# Engineering tradeoffs

The choices below fit a deterministic, locally runnable engineering simulation. They are not claims that the same choices are optimal for every production workcell.

| Area | Chosen approach and rationale | Limitation | Likely production evolution |
|---|---|---|---|
| Simulation vs physical hardware | Deterministic simulated devices make complete cycles, failures, and recovery reproducible without specialized equipment. | Simulated timing and failure modes do not capture electrical, mechanical, or environmental behavior. | Add hardware-in-the-loop rigs and validated device adapters while retaining simulation for regression tests. |
| HAL vs vendor SDK | Small C++ interfaces isolate sequence logic from robot, conveyor, gripper, and sensor implementations. | The abstractions omit vendor-specific configuration, diagnostics, and real-time fieldbus concerns. | Implement vendor adapters behind the HAL and extend interfaces only for proven hardware needs. |
| Classical vision vs deep learning | Transparent geometric checks produce deterministic pass/fail reasons with no model runtime or GPU. | The approach is not robust to complex real-world variation, occlusion, lighting, or broad defect classes. | Evaluate calibrated classical pipelines or versioned ML inference only against representative data and acceptance criteria. |
| Synthetic PGM vs camera acquisition | Small PGM fixtures are portable, reviewable, and stable in CI. | They omit exposure, optics, calibration, transport, and acquisition failures. | Add an `IInspectionSystem` camera adapter plus recorded-image and hardware-in-the-loop test suites. |
| C++ controller vs all C# | C++ keeps deterministic lifecycle, safety, sequence, and device interaction in a conventional controls boundary. | A second runtime and IPC boundary add packaging and diagnostics work. | Retain the control boundary when integrating native/vendor libraries; formalize scheduling and real-time guarantees where required. |
| TCP vs named pipes | Loopback TCP uses one protocol and test path on Windows and Linux. | Port selection and socket lifecycle require care, and the protocol is not a security boundary. | Use a hardened local transport or platform-specific IPC if deployment constraints justify the added implementations. |
| TCP vs gRPC/protobuf | NDJSON request/response messages keep the small protocol inspectable and dependency-light. | Hand-maintained schemas provide less generated compatibility tooling and streaming support. | Introduce a versioned IDL such as protobuf if the protocol gains multiple clients, streaming, or substantial schema growth. |
| Polling vs SignalR | Periodic REST polling is simple, bounded, and sufficient for the local dashboard. | Updates are not instantaneous and repeated requests add overhead. | Add server-pushed telemetry for larger deployments or tighter HMI update requirements while preserving command/query separation. |
| Single ASP.NET service vs microservices | One service cleanly owns bridge supervision, REST, history observation, and health for a local system. | Components scale and deploy together. | Split only when independent scaling, ownership, security, or availability requirements emerge. |
| Async vs synchronous persistence | A bounded queue decouples history writes from machine commands so database latency cannot stall control. | Queue overflow or process termination can lose historical records. | Add a durable local journal/outbox and explicit retention/replay policy if guaranteed audit delivery is required. |
| PostgreSQL history vs controller state | PostgreSQL stores operational history only; safe control never depends on database availability. | A restarted controller cannot reconstruct volatile cycle state from the database. | Persist non-authoritative recipes/configuration separately; use controller-native recovery procedures for safety-critical state. |
| Automatic restart vs volatile restoration | ASP.NET performs bounded bridge restart and returns the replacement controller safely in `Offline`, without replaying uncertain commands. | Operators must reinitialize and restart production after recovery. | Add supervised reconciliation and hardware state validation before permitting any recovery transition; never blindly replay motion. |
| WPF vs web frontend | WPF provides a Windows desktop HMI while keeping control behind REST. | It is Windows-only and full UI automation is limited. | A web or cross-platform client can reuse the API if deployment requirements change. |
| In-memory recovery counters vs durable monitoring | Process-local counters expose current restart/degradation information with minimal infrastructure. | They reset with the service and are not fleet-level operational records. | Export structured metrics/events to approved production monitoring once retention and alerting requirements exist. |
